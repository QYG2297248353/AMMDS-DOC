确定了"要做什么"之后，下一个问题是"用什么做"。这个问题我们认真争论了大约一个月，评估了四条技术路线。这篇文章把当时的取舍完整记下来。

{/* truncate */}

## 四条候选路线

| 技术栈 | 优势 | 我们担心的点 |
| :--- | :--- | :--- |
| Python + Django | 开发效率高 | 部署依赖重，源码难以保护 |
| Rust + Tauri | 性能与安全性极佳 | 开发周期长，Web 生态支持有限 |
| Go + Web | 编译快，单二进制分发 | 泛型与框架生态相对较弱 |
| Java SpringBoot + Vue3 | 生态成熟，基础设施丰富 | 传统上运行时偏重 |

最终，我们选择了 **Java SpringBoot + Vue3**。后端用 SpringBoot 3.x 构建 RESTful API，前端用 Vue3 提供交互体验。

## 决定性因素：GraalVM AOT

让天平真正倾斜的，是 GraalVM Native Image 的 AOT（Ahead-of-Time，提前编译）能力。

传统 Java 应用需要用户先装 JVM。而借助 GraalVM，SpringBoot 应用可以直接编译成独立的二进制可执行文件：

- 用户下载后直接运行，**无需安装 JVM**；
- 前端打包进应用，**无需 Node.js 环境**；
- 使用内嵌数据库，**无需单独配置**。

对一个自托管产品来说，这是巨大的优势。我们已经让用户承担了"自己准备设备"的门槛，就不能再叠加"自己配运行时"的负担。同时，编译成原生二进制也有效保护了后端代码，降低源码泄露的风险。

## 第二个因素：虚拟线程

AMMDS 的典型工作场景，是同时从多个站点获取数据、解析响应、写入文件——典型的 I/O 密集型任务。

SpringBoot 的虚拟线程（Virtual Threads）和响应式编程模型，恰好适合这种场景：大量并发的 I/O 等待，可以被高效调度，而不必为每个任务占用一个沉重的系统线程。这让"同时刮削多个来源"既快又省资源。

## 事后看

今天回头看，这个选择经受住了考验：

- 插件化架构、管道式数据处理、虚拟线程调度，这些核心设计都建立在这套技术栈上，一直沿用至今；
- 原生二进制分发，让"下载即用"成为现实，显著降低了安装门槛；
- 成熟的生态，让我们能把精力放在产品逻辑上，而不是反复造轮子。

技术选型没有绝对正确的答案，只有"适不适合当下的问题"。对当时的 AMMDS 而言，Java + Vue + GraalVM 是对的。
