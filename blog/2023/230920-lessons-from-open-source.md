在成立萌森工作室之前，我们以个人开发者的身份在开源社区待了很多年。回头看，那些贡献和踩坑的经历，比任何一门课程都更直接地塑造了我们后来做产品的方式。

{/* truncate */}

## 第一课：先成为用户，再成为作者

我们最早接触的是 IYUUPlus——一款在 PT 爱好者群体中广泛使用的开源自动化工具。创始人不仅用它，还参与了 IYUUPlus-Windows 版本的开发。

这段经历带来一个朴素的认知：**好的工具，是作者自己每天在用的工具。** 当你既是用户又是作者时，你不需要调研"用户痛点"，因为你自己就困在痛点里。

后来做 AMMDS 时，我们坚持"吃自己的狗粮"——团队成员日常就用它管理自己的媒体库。这个习惯一直保留到现在，它是我们发现问题最快的方式。

## 第二课：兼容比完美更重要

开源社区里最常见的争论，是"该怎么正确地做一件事"。但真实世界从来不是按照一种方式运转的：

- 有的站点用静态页面，有的用 JavaScript 动态渲染，有的提供 API；
- Kodi、Jellyfin、Emby 的 NFO 格式存在细微差异；
- 同一个用户可能同时在用 Windows、NAS 和手机。

我们学到的做法是：**不要逼用户改变习惯，而是让产品去兼容现实。** 这直接影响了 AMMDS 后来的一项核心设计——插件化架构。刮削引擎、站点适配器、数据处理流程都可插拔，社区可以贡献第三方插件支持新站点，而不必改动核心代码。

## 第三课：把复杂度留给自己

一个工具好不好，用户感知的不是它内部有多精巧，而是自己要花多少力气。

开源社区里真正让人愿意长期留下的项目，往往有一个共同点：把复杂的部分封装起来，暴露给用户的是简单、可预期的接口。反过来，把配置负担甩给用户、把内部的概念一股脑倒出来的项目，即使功能强大，也很快会被冷落。

这条经验让我们在做 AMMDS 时反复做减法：默认设置要能跑通最常见场景，高级选项藏进二级菜单；名词说明页要写得像聊天，而不是像 API 文档。

## 从回馈到创造

开源给我们的，不只是技术，更是一种工作方式：开放、务实、尊重使用者的时间。

```text
使用 → 贡献 → 理解痛点 → 形成产品构想 → 回馈社区
```

AMMDS 就是这个循环的产物。它从 IYUUPlus、NexusPHP 这些项目身上继承了大量经验，也在成长后继续并入新的开源组件。今天你用的很多能力，背后都有社区贡献者的影子。
