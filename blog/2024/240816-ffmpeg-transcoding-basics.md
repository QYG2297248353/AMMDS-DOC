如果你用过媒体服务器，多半遇到过"播放要转码"的提示。转码是媒体库里最吃资源的一环，而 FFmpeg 是它背后的引擎。这篇讲清楚转码是怎么回事，以及为什么硬件加速值得关注。

## 先分清：转码 vs 封装

很多人把两者混为一谈：

- **封装（remux）**：只是把视频流从一种容器换到另一种（比如 MKV 换 MP4），数据本身不重新编码，几乎瞬间完成、不损画质；
- **转码（transcode）**：真正重新编码视频，比如把 4K 高码率压成手机能流畅播放的格式。这一步最耗 CPU，也最容易损失画质。

媒体服务器之所以要转码，是因为客户端的能力千差万别：电视能硬解的格式，手机浏览器未必支持。服务器只能临时转一份适配的版本。

## 软件编码与硬件编码

FFmpeg 默认用软件编码器（比如 `libx264`），全部靠 CPU 算。质量最好，但对服务器来说很慢——大量并发转码时，CPU 很快成为瓶颈。

硬件编码把这项工作交给显卡或核显里的专用电路，速度快得多。常见的几种：

| 方案 | 对应硬件 | FFmpeg 编码器 |
| :--- | :--- | :--- |
| NVENC | NVIDIA 显卡 | `h264_nvenc` / `hevc_nvenc` |
| QSV | Intel 核显 | `h264_qsv` / `hevc_qsv` |
| VAAPI | Linux 通用接口 | 依驱动而定 |
| AMF | AMD 显卡 | `h264_amf` |

用哪个，取决于你的硬件。`ffmpeg -hwaccels` 能列出可用的加速方式，`ffmpeg -encoders` 能查支持的编码器。一个典型的硬件转码命令长这样：

```bash
ffmpeg -i input.mkv -c:v h264_nvenc -preset p4 -c:a aac output.mp4
```

## 一个必须知道的取舍

硬件编码追求的是**速度**，不是极致的压缩率。同样画质下，它往往需要更高的码率——文件更大一点，换来处理速度快得多。这是很划算的买卖：转码场景要的是"现在就能播"，而不是"省下最后 10% 的体积"。

对批量处理来说，这个差别更明显。软件编码可能要几小时，硬件编码几十分钟就能跑完。

## FFmpeg 的版本节奏

值得一提的是，FFmpeg 从 6.0 版本（代号 "Von Neumann"，2023 年 2 月发布）开始，确立了**每年一个大版本**的节奏，并在大版本时提升 ABI、移除弃用超过三个版本的 API。6.0 里还加入了 QSV 和 NVENC 的 AV1 编码支持。对普通用户来说，这意味着新特性来得更规律，但也提醒我们：升级时要留意 ABI 变化。

## 和 AMMDS 的关系

AMMDS 通过内置的 FFmpeg 工具链处理媒体文件——无论是视频预处理，还是相关自动化流程，底层都依赖它。理解软硬编码的区别，能帮你判断该给服务器配什么硬件：只做整理和轻负载，CPU 足够；要跑大量并发转码，一块带 NVENC 的显卡或支持 QSV 的核显会明显更轻松。
