# WebHook

WebHook 是最通用的通知出口：不绑定具体 App，只要能接收 HTTP 请求，就能接住 AMMDS 的通知。适合对接自建服务、自动化流程或企业内部系统。

{/* truncate */}

## 渠道定位

| 项目 | 说明 |
| --- | --- |
| 页面入口 | **集成应用 → 推送通知 → WebHook** |
| 集成版本 | 页面顶部标注 `1.0.0+`，类型为「消息推送」 |
| 特点 | 多回调并存、请求完全自定义、带失败重试 |
| 适用 | 企业内部系统、自动化流水线、自建消息网关 |

## 配置项

| 配置键 | 界面名称 | 类型 | 默认值 | 说明 |
| --- | --- | --- | --- | --- |
| `webhook_enabled` | 启用状态 | 布尔 | `false` | 总开关，关闭后所有回调停止发送 |
| `webhook_retry_count` | 重试次数 | 数字 | `3` | 发送失败后的重试次数，最小为 1 |
| `webhook_retry_interval` | 重试间隔 (单位: 秒) | 数字 | `5` | 每次重试之间的等待秒数，最小为 1 |

:::tip[重试怎么配]
目标端偶发 5xx 时把重试调到 3～5 次、间隔 5～10 秒即可；如果目标端限流严格，延长间隔比增加次数更有效。
:::

## 回调服务配置

在「Webhook 服务管理」卡片点「新增」创建回调，支持同时配置多个，按需启用。

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| 服务名称 | 是 | 用于列表展示与区分不同回调 |
| 请求方式 | 是 | 如 `POST`、`GET` |
| Webhook URL | 是 | 接收通知的完整地址 |
| 描述 | 否 | 备注用途，便于维护 |
| 启用状态 | 是 | 关闭后配置保留但不再推送 |
| 请求头 | 否 | JSON 数组格式，如 `[{"key":"Content-Type","value":"application/json"}]` |
| 请求体 | 否 | JSON 格式，支持通知变量占位符 |
| 检查类型 | 否 | `状态码` 或 `响应体`，为空则不校验 |
| 检查值 | 否 | 期望的状态码，或响应体必须包含的子串 |

列表上可以直接启停、编辑、删除，并对单个回调执行「推送测试」。

## 可用变量

请求头与请求体里都可以使用下列占位符，发送时自动替换：

| 变量 | 含义 |
| --- | --- |
| `{{sign}}` | 签名，用于校验通知来源 |
| `{{title}}` | 通知标题 |
| `{{subTitle}}` | 通知副标题 |
| `{{logo}}` | Logo 图片 URL |
| `{{image}}` | 内容图片 URL |
| `{{message}}` | 消息正文 |
| `{{time}}` | 推送时间 |
| `{{type}}` | 事件类型 |

示例请求体：

```json
{
  "event": "{{type}}",
  "title": "{{title}}",
  "text": "{{message}}",
  "timestamp": "{{time}}",
  "image": "{{image}}"
}
```

## 推送测试

- 对单个回调点「推送测试」，会用测试模板发一次请求。
- 接口返回「已提交推送请求」只代表**请求已提交**，不代表目标端已成功处理。
- 真实结果看目标端日志，或把「检查类型」设为状态码 / 响应体，让系统按规则判定成功与否。

:::warning[异步提交]
测试推送是异步的。点完立刻看目标端可能还没收到，稍等几秒再看。
:::

## 通知触发场景

WebHook 与其他渠道共用同一套通知，常见场景：

- 系统消息：服务启动 / 关闭、磁盘空间不足、账户长期未登录提醒。
- 订阅与下载：订阅命中、订阅失败、已推送下载、下载完成。
- 入库与刮削：影片入库、影片刮削成功、演员刮削成功。
- 站点认证结果、测试消息。

## 系统级开关

推送前依次校验（**系统配置 → 通知**）：

| 配置键 | 界面名称 | 默认值 | 说明 |
| --- | --- | --- | --- |
| `system_notice_enable` | 启用通知推送 | `true` | 总开关，关闭后所有渠道静默 |
| `system_notice_type` | 消息类型 | 见说明 | 分类白名单，未勾选的分类不推送 |
| `system_notice_night_free` | 夜间免打扰 | `false` | 开启后 22:00 至次日 08:00 不推送 |

`system_notice_type` 默认值为 `system,subscription,download,library,certification,vip,scrape,actor_scrape`，按分类代码匹配。接入自动化流程时，建议只勾选真正需要的分类，避免回调风暴。

## 常见问题

| 现象 | 可能原因 | 处理 |
| --- | --- | --- |
| 测试推送提示已提交但目标端没收到 | 异步提交，或 URL 不可达 | 检查目标端日志与网络连通性 |
| 一直判定失败 | 检查类型/检查值与实际响应不匹配 | 改为状态码并填 `200`，或清空检查 |
| 请求头不生效 | 请求头不是合法 JSON 数组 | 按 `[{"key":...,"value":...}]` 修正 |
| 变量没被替换 | 占位符拼写错误 | 对照变量表逐字核对，注意双花括号 |
| 收到重复通知 | 目标端超时导致重试 | 缩短目标端处理时间，或减少重试次数 |

更多排查方法见[常见问题](/docs/faq)；如果希望回调只承载某一类事件，先在系统配置的「消息类型」里收窄分类，再按 `{{type}}` 在目标端分流。
