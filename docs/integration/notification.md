# 消息推送到手机

扫描完成、订阅命中、影片入库这些事，不必一直盯着后台看。接一个推送渠道，AMMDS 会在事情发生时发消息给你。

> **推送**：AMMDS 主动把一条消息送到你的手机或其它程序上，不需要你去打开查看。

> **Webhook**：一种「有事情就往指定地址发一条消息」的方式。只要对方能接收网络消息，就能接住 AMMDS 的通知。

> **机器人 / Bot**：在聊天软件里注册的一个自动账号。你给它发指令，它按指令办事。

## 先选一个渠道

| 渠道 | 适合谁 | 要准备什么 | 特别之处 |
| --- | --- | --- | --- |
| Bark | 用 iPhone 的人，想最省事 | 装 Bark App，复制设备密钥 | 一个密钥就能收消息 |
| Telegram | 想用手机指令远程操作的人 | 向 `@BotFather` 建机器人，拿 Bot Token 与 Chat ID | **唯一支持反向控制**，能用指令检索、订阅、跑任务 |
| Webhook | 想把消息接到自建服务或自动化流程的人 | 一个能接收网络消息的地址 | 可以同时配多个回调，请求内容完全自定义 |

:::warning[还有三道总开关]
配好渠道只是第一步。消息是否真的发出去，还要过系统级开关（见下文「三道系统级开关」）。一条都收不到时，先去那里看。
:::

## Bark

Bark 是 iOS 上的轻量推送工具，一个设备密钥就能收通知。

| 项目 | 说明 |
| --- | --- |
| 入口 | 集成应用 → 推送通知 → Bark |
| 目标设备 | iOS（Bark App） |
| 服务形态 | 官方 `api.day.app`，或你自己搭建的服务端 |

### 设置项说明

| 设置项 | 要填什么 | 不填 / 填错会怎样 |
| --- | --- | --- |
| 启用状态 | 打开开关 | 关闭后推送测试返回「请启用 Bark 插件」，通知也不再走这个渠道 |
| 服务地址 | 默认 `https://api.day.app`；自建服务端改成你的地址 | 地址与密钥不同源时请求会被拒绝 |
| 设备密钥 | Bark App 首页显示的推送地址里，`api.day.app/` 之后的那一段 | 不填或填错，推送测试失败 |
| 通知图标 | 默认使用 AMMDS 图标；可换成别的图片地址 | 地址不可访问时通知没有图标 |
| 通知分组 | 默认 `AMMDS`；同一分组的通知在通知中心折叠在一起 | 清空后不再分组 |
| Markdown 优先 | 默认关闭；打开后正文按 Markdown 渲染 | 老版本 App 上可能出现排版错乱，遇到先关掉 |

### 按钮

| 按钮 | 检查内容 |
| --- | --- |
| 测试连接 | 只确认服务地址能连上，不检查设备密钥 |
| 推送测试 | 用测试模板真实发一条推送，验证密钥与服务端 |

还能查服务端状态，看到版本、程序信息和**已注册设备数**，用来判断服务端是否正常。

:::tip[自建服务端要注意]
用自建服务端时，「服务地址」要改成自建地址，密钥以自建服务端显示的为准；两者不匹配会被拒绝。
:::

## Telegram

Telegram 是主力通知渠道，也是唯一支持反向控制的渠道：除了收通知，还能用指令办事。

| 项目 | 说明 |
| --- | --- |
| 入口 | 集成应用 → 推送通知 → Telegram |
| 消息形态 | 文本 + 图片，图片可加剧透蒙版 |
| 双向能力 | 推送通知 + 机器人指令控制 |
| 密钥在哪拿 | 在 Telegram 搜索 `@BotFather`，按提示创建机器人，复制它给你的 Token |

### 设置项说明

| 设置项 | 要填什么 | 不填 / 填错会怎样 |
| --- | --- | --- |
| 启用状态 | 打开开关 | 关闭后所有 Telegram 操作都会提示「请启用 Telegram 插件」 |
| 服务地址 | 默认 `https://api.telegram.org`，可改为自建反向代理 | 改错会连不上 |
| Bot Token | `@BotFather` 创建机器人后签发的令牌 | 为空时取不到 Chat ID，也发不出消息 |
| Chat ID | 接收消息的私聊、群组或频道 ID；私聊 ID 是正数，群组与频道通常是负数 | 填错表现为「推送测试成功但收不到消息」；群组里要先把机器人拉进群 |
| Webhook URL | 回调地址，留空表示不注册回调 | 注册前必须在系统配置里完成域名绑定，否则会被直接拒绝 |
| 剧透模式 | 默认关闭；消息含图片时加剧透蒙版 | 关闭就是直接显示图片 |

### 按钮

| 按钮 | 作用 | 前置条件 |
| --- | --- | --- |
| 获取 Chat ID | 读取机器人最近一次会话的 Chat ID | 已填 Bot Token，且已给机器人发过消息 |
| 注册指令 | 把指令菜单注册到机器人 | 已填服务地址与 Bot Token |
| 注册 Webhook | 把回调地址注册到 Telegram | 系统配置中已完成**域名绑定** |
| 推送测试 | 用测试模板发一条消息 | 已填 Bot Token 与 Chat ID |
| 测试连接 | 确认服务地址能连上 | 无 |

重复点「注册指令」不会重复添加：只要指令表里的指令都已存在，就不会再提交；只要有任意一条缺失，就会把整套重新提交，此时你自定义的同名指令会被覆盖。

完整指令清单、权限与二次确认规则见 [用 Telegram 遥控 AMMDS](./telegram-commands)。

:::warning[Webhook 需要公网可达]
注册 Webhook 前必须在系统配置中完成域名绑定，否则会被直接拒绝。家庭内网部署建议不注册 Webhook，改用默认方式接收指令。
:::

## Webhook

Webhook 是最通用的出口：不绑定具体 App，只要能接收网络消息，就能接住 AMMDS 的通知。

| 项目 | 说明 |
| --- | --- |
| 入口 | 集成应用 → 推送通知 → Webhook |
| 特点 | 多回调并存、请求完全自定义、带失败重试 |
| 适用 | 企业内部系统、自动化流水线、自建消息网关 |

### 设置项说明（插件级）

| 设置项 | 要填什么 | 不填 / 填错会怎样 |
| --- | --- | --- |
| 启用状态 | 打开开关 | 关闭后所有回调停止发送 |
| 重试次数 | 默认 `3`；发送失败后的重试次数，最小为 1 | 目标端偶发故障时调大更有用 |
| 重试间隔 | 默认 `5` 秒；每次重试之间等待的秒数，最小为 1 | 目标端限流严格时，延长间隔比增加次数更有效 |

### 设置项说明（每一个回调）

在「Webhook 服务管理」卡片点「新增」创建回调，可以同时配多个，按需启用。

| 设置项 | 要填什么 | 不填 / 填错会怎样 |
| --- | --- | --- |
| 服务名称 | 用于列表展示与区分不同回调 | 必填；为空无法区分 |
| 请求方式 | 如 `POST`、`GET` | 必填；与对方要求不符会被拒 |
| Webhook URL | 接收通知的完整地址 | 必填；不可达时推送失败并重试 |
| 描述 | 备注用途 | 选填 |
| 启用状态 | 关闭后配置保留但不再推送 | 关闭就收不到 |
| 请求头 | 告诉对方这条消息是什么格式，按 JSON 数组填，例如 `[{"key":"Content-Type","value":"application/json"}]` | 格式不是 JSON 数组时不生效 |
| 请求体 | 真正发给对方的内容，按 JSON 写，可以用下面的变量占位 | 写错不会报错，只是对方收到的内容不对 |
| 检查类型 | 判断成功的方式：看状态码，或看对方回复里有没有某段文字；留空就是不判断 | 判定方式与实际不符会一直显示失败 |
| 检查值 | 期望看到的状态码，或对方回复里必须包含的那段文字 | 同上 |

列表上可以直接启停、编辑、删除，并对单个回调执行「推送测试」。

### 可用变量

请求头与请求体里都能用下面这些占位符，发送时自动替换：

| 变量 | 含义 |
| --- | --- |
| `{{sign}}` | 签名，用来确认通知确实来自 AMMDS |
| `{{title}}` | 通知标题 |
| `{{subTitle}}` | 通知副标题 |
| `{{logo}}` | Logo 图片地址 |
| `{{image}}` | 内容图片地址 |
| `{{message}}` | 消息正文 |
| `{{time}}` | 推送时间 |
| `{{type}}` | 事件类型 |

请求体示例：

```json
{
  "event": "{{type}}",
  "title": "{{title}}",
  "text": "{{message}}",
  "timestamp": "{{time}}",
  "image": "{{image}}"
}
```

:::warning[「已提交」不等于「已收到」]
推送测试返回「已提交推送请求」只代表请求已发出，不代表对方已成功处理。真实结果看对方日志；也可以把「检查类型」设为状态码或响应体，让系统按规则判定。
:::

## 三道系统级开关

推送前会依次检查这三道开关（**系统配置 → 通知**）：

| 设置项 | 要填什么 | 不填 / 填错会怎样 |
| --- | --- | --- |
| 启用通知推送 | 默认**开启**；是总开关 | 关闭后所有渠道静默，一条都不发 |
| 消息类型 | 允许推送的消息分类，多个用英文逗号分隔。默认 `system,subscription,download,library,certification,vip,scrape,actor_scrape` | 没列进去的分类不会推送 |
| 夜间免打扰 | 默认关闭；开启后 22:00 至次日 08:00 不推送 | 这段时间内的通知按「无需推送」跳过，**不会排队补发** |

:::note[被开关跳过不算失败]
夜间免打扰或分类未勾选时，系统按「无需推送」处理并记录日志，不会报错，也不会补发。
:::

## 哪些事会发通知

三个渠道共用同一套通知内容：

| 分类 | 触发场景 |
| --- | --- |
| 系统消息 | 服务启动 / 关闭、磁盘空间不足、账户长期未登录提醒 |
| 订阅消息 | 订阅命中资源、订阅失败 |
| 下载消息 | 已推送下载、下载完成 |
| 入库消息 | 影片入库完成 |
| 认证消息 | 站点认证结果 |
| 影片刮削 | 刮削成功 |
| 演员刮削 | 演员刮削成功 |
| 测试消息 | 手动推送测试 |

## 出问题了怎么办

- **一条都收不到**：先检查系统配置里的「启用通知推送」是否打开，再看当前是否处于夜间免打扰时段，最后确认消息分类在允许列表里。
- **推送测试失败**：Bark 检查设备密钥与地址是否同源；Telegram 检查 Bot Token 与 Chat ID；Webhook 检查地址是否可达。
- **Telegram 推送成功但手机没消息**：Chat ID 属于别的会话，或机器人被踢出群。重新「获取 Chat ID」并核对（先给机器人发一条消息）。
- **获取 Chat ID 失败**：还没给机器人发过消息，先私聊机器人发一条再点按钮。
- **注册 Webhook 被拒绝**：系统配置里没完成域名绑定。
- **Webhook 一直判定失败**：检查类型 / 检查值与实际响应不匹配，改成状态码并填 `200`，或清空检查。
- **变量没被替换**：占位符拼写错误，对照变量表逐字核对，注意是两对花括号。
- **收到重复通知**：对方超时导致重试，缩短对方处理时间或减少重试次数。
- **指令菜单是旧的**：之前已注册过部分指令，先删除再重新注册。
