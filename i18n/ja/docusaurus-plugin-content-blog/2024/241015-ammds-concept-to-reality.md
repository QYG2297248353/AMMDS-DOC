# AMMDS が概念から現実へ：製品誕生物語

今日は、AMMDS の舞台裏についてお話ししたいと思います。漠然としたアイデアから最終的な製品まで、この開発の道のりは課題、決断、そして成長に満ちたものでした。

## 市場のニーズ：既存のツールではまだ不十分

物語の起点は、私たち自身の「痛み」でした。萌森スタジオのチームメンバーは全員が熱心なセルフホスティングユーザーであり、日々 IYUUPlus を使ってサイトのリソース管理を行っている中で、共通する問題を発見しました。

**メディア管理のツールチェーンが分断されている。**

映画のメタデータをスクレイプするには TinyMediaManager、ドラマの情報を処理するには MediaElch、サイトのリソース管理には別のツール、そして NFO ファイルの形式の一貫性を保つためにはさらに別のツールが必要です。それぞれのツールが独自のデータ形式と操作ロジックを持っており、データがツール間を移動するたびに情報が頻繁に失われました。

さらに重要なのは、既存のツールの多くは統一されたダッシュボードと自動化の機能を欠いていることです。一か所ですべてのメディアファイルのメタデータ状態を確認することも、誤ったスクレイピング結果を一括で修正することもできません。数十 TB のメディアライブラリを持つヘビーユーザーにとって、この分断による保守コストは驚くべきものです。

## 技術選定：なぜ Java SpringBoot + Vue3 を選んだのか

何を作るかが決まった後、次の問題はどの技術で実装するかでした。

私たちは一か月にわたる技術調査を行い、複数の技術スタックを評価しました。

- **Python + Django**：開発効率は高いが、配布時の依存が重く、ソースコードを保護しにくい
- **Rust + Tauri**：性能とセキュリティは極めて優れるが、開発期間が長く、Web エコシステムのサポートが限られている
- **Go + Web**：コンパイルが速く、単一バイナリで配布できるが、ジェネリクスとフレームワークのエコシステムが比較的弱い
- **Java SpringBoot + Vue3**：成熟したエコシステム、豊富なインフラストラクチャ、GraalVM AOT ネイティブコンパイルによるバイナリ化でコードを保護

最終的に私たちは **Java SpringBoot + Vue3** の組み合わせを選びました。バックエンドは SpringBoot 3.x フレームワークで RESTful API を構築し、フロントエンドは Vue3 で現代的な操作体験を提供します。GraalVM Native Image の AOT（Ahead-of-Time）コンパイル技術により、SpringBoot アプリケーションは単独で動作するバイナリ実行ファイルへ直接コンパイルでき、ユーザーはダウンロード後に JVM ランタイムをインストールすることなく直接実行できます。これはセルフホスティングのシナリオにおいて大きな利点です。ユーザーは Java ランタイムや Node.js 環境をインストールする必要も、データベースを設定する必要もありません。

同時に、SpringBoot の仮想スレッド（Virtual Threads）とリアクティブプログラミングモデルは、スクレイピングタスクの処理に非常に適しています。AMMDS の典型的な作業シナリオは、複数のサイトから同時にデータを取得し、レスポンスを解析し、ファイルへ書き込むことであり、このような I/O 集約型のタスクは仮想スレッドのスケジューリングモデル下で非常に優れた性能を発揮します。また、GraalVM のネイティブバイナリはバックエンドコードを効果的に保護し、ソースコードの漏洩を防ぐこともできます。

## 重要な意思決定の節目

### 第一の決断：プラグイン化アーキテクチャ

プロジェクト設計の初期段階で、私たちは**プラグイン化アーキテクチャ**を中核の設計原則として確立しました。これは、AMMDS のスクレイピングエンジン、サイトアダプター、データ処理フローがすべて差し替え可能であることを意味します。ユーザーは必要に応じてさまざまなプラグインをインストールでき、コミュニティもサードパーティ製のプラグインを提供して機能を拡張できます。

この決断は、その後の開発において極めて正しかったことが証明されました。AMMDS が複数の PT サイトやメタデータ源に迅速に対応できているのは、プラグイン化アーキテクチャにより、コアコードを変更することなくプラグインを書くだけで新しいサイトをサポートできるためです。

### 第二の決断：Web ダッシュボード優先

従来のメディア管理ツールとは異なり、私たちはデスクトップクライアントではなく、Web ダッシュボードを AMMDS の主要な操作インターフェースとすることにしました。これにより、ユーザーはどのデバイスからでもメディアライブラリを管理できます。PC、タブレット、スマートフォン、さらには NAS のブラウザ経由でもアクセス可能です。

Web ダッシュボードの設計は「モバイルファースト」の理念にも従っており、スマートフォンの画面でも良好な操作体験を確保しています。

### 第三の決断：NFO 標準への対応

コミュニティでは NFO ファイルの形式をめぐって常に議論がありました。Kodi の NFO 形式、Jellyfin の NFO 形式、Emby の NFO 形式の間には微細な違いがあります。私たちは**主要なすべての形式に同時に対応**することにし、ユーザーが設定で目的の形式を選択すると、システムが自動的に適応します。

## 最初のプロトタイプ

2023 年末、AMMDS の最初の動作するプロトタイプが生まれました。このバージョンには最も基本的な機能しかありませんでした。

- 単一のサイトから torrent 一覧を取得する
- torrent に含まれるメタデータ情報を解析する
- 基本的な NFO ファイルを生成する

機能は質素でしたが、中核となる技術ルートの実現可能性を検証しました。今日振り返ると、このプロトタイプのコードの多くはすでに何度も書き直されていますが、中核のアーキテクチャ設計——プラグイン化エンジン、パイプライン型のデータ処理、仮想スレッドに基づくスケジューリングシステム——は今日まで受け継がれています。

## 開発における課題

### 課題一：サイトの互換性

PT サイトはそれぞれ独自のページ構造、認証方式、データ形式を持っています。静的ページを使うサイトもあれば、JavaScript による動的レンダリングを使うサイト、API インターフェースを使うサイトもあります。異なるサイトに対応するため、私たちは柔軟なアダプターメカニズムを開発し、サイトごとに独立した解析ルールを記述できるようにしました。

### 課題二：データの一貫性

複数のソースから同じ映画のメタデータを同時に取得した場合、どのようにマージし重複を排除するかは厄介な問題です。私たちは**優先度ルールエンジン**を設計しました。ユーザーは異なる情報源の優先度をカスタマイズでき、システムはルールに従って自動的にデータをマージします。

### 課題三：性能の最適化

大規模なメディアライブラリ（数万件）を処理する際、メモリ使用量とスキャン速度がボトルネックとなりました。増分スキャン、キャッシュ機構、バッチ処理戦略を導入することで、全量スキャンの時間を数時間から数十分へと短縮しました。

## 製品の進化

最初のプロトタイプから今日の AMMDS まで、製品は無数のイテレーションとリファクタリングを経てきました。すべてのバージョンアップは、ユーザーからの実際のフィードバックと開発者自身の使用体験に起因しています。私たちは「ドッグフーディング」を貫いています。チームメンバーは日常的に AMMDS を使って自分のメディアライブラリを管理しており、これにより問題や改善の方向性をいち早く発見できます。

AMMDS は依然として急速にイテレーションを続けています。今後は、より多くのインテリジェントなメタデータ処理機能を導入し、プラグインエコシステムをさらに充実させ、セルフホスティングによるメディア管理をより簡単で効率的なものにしていきます。
