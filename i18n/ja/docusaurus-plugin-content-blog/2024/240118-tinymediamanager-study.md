プロジェクト立ち上げ時に同種のツールを調査した際、TinyMediaManager（略称 TMM）は私たちが繰り返し研究した対象でした。これは Java で書かれた無料のオープンソースのメディア管理ツールで、Windows、Linux、macOS を横断して動作します。私たちの競合相手ではなく、非常に良い「教科書」でした。

## これはいったい何をするものか

TMM の核となる位置づけは、**ローカルのメディアライブラリを整理し、メタデータ、カバー画像、ファイル構造を整えて準備する**ことです。Kodi、Plex、Emby、Jellyfin などのメディアセンターで利用するために、です。言い換えれば、AMMDS とエコシステムの同じ層にあります——どちらも「再生」ではなく「整理」を担うのです。

公開されている機能一覧を見ると、いくつかの点が非常にしっかりしています：

- **複数ソースからのスクレイピング**：IMDb、TheMovieDB、TVDb、OFDb、Moviemeter、Trakt など複数のメタデータソースに対応；
- **素材のダウンロード**：ポスター、背景画像、ロゴ、そして FanArt.tv のアート画像；
- **字幕**：OpenSubtitles.org から取得；
- **技術情報**：MediaInfo ライブラリでエンコード、再生時間、解像度などを抽出し、NFO に書き込む；
- **一括リネーム**：ユーザーが定義した形式に従って、ファイル名とディレクトリを自動的に整理；
- **NFO 出力**：すべての情報を Kodi 互換の NFO ファイルに自動的に書き込む；
- **二つのインターフェース**：グラフィカルインターフェースとコマンドラインインターフェースの両方を備える。

## 学ぶべき三つの点

### 第一に、データがソフトウェアに閉じ込められていないこと

TMM はすべてを NFO ファイルに書き出し、独自のプライベートデータベースに閉じ込めません。この点に私たちは強く共感します——**ユーザーのデータは持ち出せるべきだ**。これが AMMDS が標準 NFO と標準バックアップパッケージにこだわる根本的な理由です。

### 第二に、複数ソース＋手動修正

複数のメタデータソースに対応しつつ、ユーザーがどのフィールドでも手動で編集できるようにしています。この組み合わせが重要です。自動スクレイピングが効率を担い、手動修正が正確さを担うからです。私たちが後に[優先度ルールエンジン](/blog/plugin-architecture)をつくったときも、同じ発想で進めました。

### 第三に、クロスプラットフォームは JVM によるもの

TMM は Java アプリケーションで、Java ランタイム（少なくとも JRE 8）に依存するため、当然ながらクロスプラットフォーム対応です。これは[技術選定](/blog/tech-stack-decision)で私たちが Java エコシステムを重視した判断を裏付けるものです——ただし私たちは GraalVM を使ってランタイム自体もパッケージに含め、ユーザーが JRE をインストールする必要すらないようにしました。

## 私たちとの違い

TMM はデスクトップアプリケーションですが、AMMDS は最初から**セルフホスト＋Web パネル**の形をとり、NAS や常時稼働の機器上で動き、ブラウザからアクセスします。これは製品の位置づけの違いであり、優劣ではありません——自分のマシンでひとつのフォルダを整理したいだけなら TMM で十分ですし、家族全員の機器からいつでもメディアライブラリを管理したいなら、AMMDS のようなサービスが必要です。

巨人の肩に立つことで、私たちは遠回りを減らせました。TMM が検証した多くの手法が、今日では AMMDS の設計にも反映されています。
