Kodi や Jellyfin を使ったことがあれば、映画のディレクトリの中に動画と同じ名前の `.nfo` ファイルを見たことがあるはずです。一見なんの変哲もないファイルですが、セルフホストのメディアライブラリ全体のエコシステムにおいて、最も重要な「共通言語」なのです。

## 名前と本質

NFO は "Info"（情報）の略です。独自の形式ではなく、本質的には **XML テキストファイル**です——中にはタグのペアが並び、その作品のタイトル、あらすじ、出演者、公開年などの情報が記されています。

ファイル自体は何も「する」わけではなく、単に情報を保管しているだけです。しかし、プレーンテキストで統一された構造を持つため、さまざまなソフトウェアが読み解けます。Kodi の公式 Wiki では、これを「メタデータをライブラリに取り込む方法のひとつ」と定義しています。スキャン時にメディアディレクトリに正しく命名された NFO ファイルがあれば、Kodi はネットワークから取得するのではなく、まずそれを読み込みます。

## 三種類の NFO

NFO は一種類だけだと思っている人が多いですが、実際には内容によって三種類に分けられます：

| 種類 | 中身 | 用途 |
| :--- | :--- | :--- |
| メタデータ NFO | 作品情報の完全なタグ | 最も一般的で、メタデータをそのまま取り込む |
| 解析 NFO | ライブラリを指す URL のみ | スクレイパーに「欲しいのは実はこの作品だ、間違えるな」と伝える |
| ハイブリッド NFO | URL＋一部の上書きフィールド | まず URL から取得し、その後タイトルや再生時間など少数のフィールドを上書きする |

解析 NFO は特に便利です。たとえば同じサイト内に同名のバージョンが数十あり、自動一致がいつも間違えるような場合——正しい URL だけを含む NFO を置けば、強制的に指定できます。これは私たちが[手動一致](/blog/nfo-compatibility)機能をつくったときに対応したのと同じ種類の問題です。

## つまずきやすい細かい点

- **エンコード**：NFO ファイルは UTF-8 で保存するのが原則です。Windows のメモ帳は既定で ANSI として保存することがあり、英語以外の文字が文字化けします。
- **命名**：通常は動画ファイルと同じ名前にします（例：`Jumanji.mp4` に対応する `Jumanji.nfo`）；テレビシリーズには `tvshow.nfo`、アルバムには `album.nfo` を使います。
- **変更後は再読み込みが必要**：ライブラリを一度スキャンすると、NFO はバックアップ的な役割に後退します。ファイルの内容を変更しても、そのレコードを手動で更新して初めて再読み込みされます。
- **汎用性**：Kodi だけでなく、Plex、Emby、Jellyfin、TinyMediaManager なども Kodi 形式の NFO を認識できます。これがまさにその価値です——ひとつのファイルが複数の場所で使えます。

## AMMDS がこれを重視する理由

私たちが NFO 互換性に取り組んでいるのは、この「持ち運び可能性」に着目したからです。ユーザーが AMMDS で整理した資料は、ある日プレーヤーを替えたり、システムを再インストールしたりしても、NFO ファイルさえ残っていればデータは失われません。これは私たちが[セルフホスト](/blog/why-self-hosted)や[標準バックアップパッケージ](/docs/backend/system/backup-restore)にこだわるのと同じ発想です——**データは持ち出せるべきだ**。

> 注：本稿の NFO の定義と分類は Kodi 公式 Wiki に基づいてまとめたものです。具体的なタグと命名規則は Kodi のドキュメントを基準としてください。
