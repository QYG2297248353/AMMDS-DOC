萌森スタジオを設立する前、私たちは個人開発者として長年オープンソースコミュニティに身を置いていました。振り返れば、貢献やつまずきを重ねた経験は、どんな授業よりも直接的に、その後の私たちのものづくりの形を整えてくれました。

{/* truncate */}

## 第一の授業：まずユーザーになり、それから作者になる

私たちが最初に触れたのは IYUUPlus——PT 愛好家の間で広く使われているオープンソースの自動化ツールでした。創設者はこれを使うだけでなく、IYUUPlus-Windows 版の開発にも参加しました。

この経験から、素朴な気づきが生まれました：**良いツールとは、作者自身が毎日使っているツールである。** あなたがユーザーであり同時に作者であるとき、「ユーザーの痛み」を調査する必要はありません。なぜなら、あなた自身がその痛みの中にいるからです。

その後 AMMDS をつくる際、私たちは「ドッグフーディング」（自分で使い込むこと）を貫きました——チームのメンバーは日々これで自分のメディアライブラリを管理しています。この習慣は今も続いており、問題を最も早く見つける方法です。

## 第二の授業：互換性は完璧さより重要

オープンソースコミュニティで最もよく見られる議論は、「物事を正しく行うにはどうすればよいか」というものです。しかし現実世界は、決して一つのやり方で動いてはくれません：

- 静的ページを使うサイトもあれば、JavaScript で動的に描画するサイト、API を提供するサイトもあります；
- Kodi、Jellyfin、Emby の NFO 形式には微妙な違いがあります；
- 同じユーザーが Windows、NAS、スマートフォンを同時に使っている場合もあります。

私たちが学んだのは、**ユーザーに習慣を変えさせるのではなく、製品の方を現実に合わせる**という姿勢です。これはその後の AMMDS の核となる設計、プラグイン化アーキテクチャに直接影響しました。スクレイピングエンジン、サイトアダプター、データ処理フローはすべて差し替え可能で、コミュニティはコアコードを変更することなく、新しいサイトに対応するサードパーティ製プラグインを提供できます。

## 第三の授業：複雑さは自分たちの側に残す

ツールの良し悪しをユーザーが感じ取るのは、その内部がどれだけ精巧かではなく、自分がどれだけの手間をかけねばならないかです。

オープンソースコミュニティで本当に人が長くとどまりたくなるプロジェクトには、往々にして共通点があります。複雑な部分をカプセル化し、ユーザーに見せるのはシンプルで予測可能なインターフェースです。逆に、設定の負担をユーザーに押し付け、内部の概念をすべてさらけ出すプロジェクトは、機能が強力でもすぐに敬遠されます。

この経験から、私たちは AMMDS をつくる際に繰り返し引き算を行いました。既定設定で最も一般的なシナリオが動くようにし、高度なオプションは二段目のメニューに隠す。用語の説明ページは API ドキュメントではなく、会話のような書き方にする——そう心がけました。

## 還元から創造へ

オープンソースが私たちに与えてくれたのは、技術だけではありません。開放性、実用性、そして利用者の時間を尊重するという働き方そのものです。

```text
使用 → 貢献 → 痛みを理解 → 製品の構想を形成 → コミュニティに還元
```

AMMDS はこの循環の産物です。IYUUPlus や NexusPHP といったプロジェクトから多くの経験を受け継ぎ、成長した後も新たなオープンソースコンポーネントを取り込み続けています。今日あなたが使っている多くの機能の背景には、コミュニティの貢献者の影があります。
