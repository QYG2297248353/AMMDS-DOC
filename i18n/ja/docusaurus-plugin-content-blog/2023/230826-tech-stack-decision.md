「何を作るか」が決まった後、次の問題は「何で作るか」でした。この問題について私たちは約一か月にわたって真剣に議論し、四つの技術ルートを評価しました。この記事では、当時の取捨選択を余すところなく記録します。

{/* truncate */}

## 四つの候補ルート

| 技術スタック | 利点 | 私たちが懸念した点 |
| :--- | :--- | :--- |
| Python + Django | 開発効率が高い | 配布時の依存が重く、ソースコードを保護しにくい |
| Rust + Tauri | 性能と安全性が極めて優れる | 開発期間が長く、Web エコシステムのサポートが限られている |
| Go + Web | コンパイルが速く、単一バイナリで配布できる | ジェネリクスとフレームワークのエコシステムが比較的弱い |
| Java SpringBoot + Vue3 | エコシステムが成熟し、インフラストラクチャが豊富 | 従来はランタイムが重い傾向がある |

最終的に、私たちは **Java SpringBoot + Vue3** を選びました。バックエンドは SpringBoot 3.x で RESTful API を構築し、フロントエンドは Vue3 で操作体験を提供します。

## 決め手：GraalVM AOT

天平が本当に傾いたのは、GraalVM Native Image の AOT（Ahead-of-Time、事前コンパイル）能力によるものです。

従来の Java アプリケーションでは、ユーザーが先に JVM をインストールする必要がありました。しかし GraalVM を使えば、SpringBoot アプリケーションを単独で動作するバイナリ実行ファイルへ直接コンパイルできます：

- ユーザーはダウンロード後すぐに実行でき、**JVM のインストールは不要**；
- フロントエンドはアプリケーションに同梱され、**Node.js 環境は不要**；
- 組み込みデータベースを使用し、**個別の設定は不要**。

セルフホスト製品にとって、これは大きな利点です。私たちはすでにユーザーに「自分で機器を用意する」という敷居を負わせている以上、「自分でランタイムを設定する」という負担をさらに上乗せすることはできません。同時に、ネイティブバイナリへのコンパイルはバックエンドコードを効果的に保護し、ソースコード漏洩のリスクを低減します。

## 第二の要素：仮想スレッド

AMMDS の典型的な作業シナリオは、複数のサイトから同時にデータを取得し、レスポンスを解析し、ファイルへ書き込むことです——典型的な I/O 集約型タスクです。

SpringBoot の仮想スレッド（Virtual Threads）とリアクティブプログラミングモデルは、まさにこのようなシナリオに適しています。大量に同時発生する I/O 待機を効率的にスケジュールでき、各タスクに重いシステムスレッドを割り当てる必要がありません。これにより「複数のソースを同時にスクレイピングする」ことが高速かつ省リソースで実現できます。

## 後から振り返って

今日振り返れば、この選択は試練に耐えてきました：

- プラグイン化アーキテクチャ、パイプライン型のデータ処理、仮想スレッドによるスケジューリングといった中核設計はすべてこの技術スタックの上に構築され、今日まで使い続けられています；
- ネイティブバイナリによる配布は「ダウンロードしてすぐ使える」ことを現実のものとし、インストールの敷居を大幅に下げました；
- 成熟したエコシステムにより、私たちは車輪の再発明を繰り返すのではなく、製品のロジックに集中できました。

技術選定に絶対的に正しい答えはなく、「その時点の問題に適しているかどうか」があるだけです。当時の AMMDS にとって、Java + Vue + GraalVM は正しい選択でした。
