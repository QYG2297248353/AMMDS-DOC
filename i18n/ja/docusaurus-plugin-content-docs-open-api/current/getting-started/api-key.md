# まず鍵を手に入れる

ほかのプログラムに AMMDS のデータを読ませるには、最初に「鍵」が必要です。このページでは、鍵とは何か、どう手に入れるか、どう保管するか、なくしたらどうするかを説明します。

そもそも鍵が必要か分からない場合は、先に[オープンプラットフォームでできること](./overview.md)をお読みください。

## まず言葉を整理します

> **API キー**：文字の羅列で、家の鍵のようなものです。持っている人は、その権限の範囲でデータを読めます。AMMDS は「誰か」ではなく「その文字列が正しいか」だけを見ます。

> **認証**：入る前に身分を示すことです。オープン API では、リクエストに鍵を入れて送ることがこれに当たります。

> **ヘッダー**：本文とは別に、リクエストといっしょに送る小さな付加情報です。「鍵はこれ」「形式はこれ」といったことを伝えるのに使います。

## 三つの手順で鍵を手に入れます

### 手順 1：オープン API を有効にする

1. AMMDS の管理画面にログインし、**システム → システム設定** を開きます。
2. オープン API のスイッチ（設定キー `GLOBAL_OPEN_API`）を ON にします。
3. 設定を保存します。

:::warning[二つの条件がそろって初めて通れます]
リクエストに有効な `x-api-key` が入っていること、**かつ**オープン API のスイッチが ON であること。どちらか欠けると入れてもらえません。
:::

### 手順 2：鍵を作る

1. **システム → 鍵管理** を開きます。
2. 鍵の作成を選びます。
3. 名前には後から見分けられる用途を書きます。例：「バックアップスクリプト」。
4. 種別は **X-API-KEY**（`secret_x_api_key`）を選びます。
5. 保存したら**すぐに鍵をコピー**してください。画面を閉じると、もう全文は見られません。

:::note[鍵の種別は独立しています]
鍵管理にはほかに「AMMDS アシスタント」と「Mihon 拡張」という種別があります。**Mihon** 用の認証コードは `/api/mihon` でしか使えず、`/api/v1` では呼び出せません。それ以外の種別（X-API-KEY、AMMDS アシスタントを含む）は技術的に `/api/v1` で使えます。ただしオープン API には **X-API-KEY** の使用を推奨します。用途が明確で、問題の切り分けがいちばん簡単だからです。
:::

### 手順 3：リクエストに鍵を載せる

コマンドラインからの完全な呼び出しです。`<あなたの鍵>` をコピーした文字列に置き換えてください。

```bash
curl -H "x-api-key: <あなたの鍵>" \
  "http://127.0.0.1:8080/api/v1/movie/count"
```

| 項目 | 値 |
| --- | --- |
| ヘッダー名 | `x-api-key`（小文字、途中はハイフン） |
| 対象範囲 | `/api/v1/**` のみ |
| 鍵が不要な住所 | `/api/v1/health/**` |

## 設定項目

| 設定項目 | 何を入れるか | 入れない / 間違えた場合 |
| --- | --- | --- |
| オープン API のスイッチ | システム → システム設定で ON か確認。設定キー `GLOBAL_OPEN_API`（既定は ON） | OFF のままだと正しい鍵でも拒否されます |
| 鍵の名前 | 何でもよいですが、用途を書くと後で見分けやすいです | 動作には影響しません。ただ後で区別しづらくなります |
| 鍵の種別 | **X-API-KEY** を推奨 | Mihon 種別は `/api/v1` で使えません。他の種別は使えますが非推奨です |
| 鍵の文字列 | 作成時にコピーした全文 | 一字欠けたり余分な空白が入ったりすると認証に失敗します |
| ヘッダー名 | 必ず `x-api-key` | `api-key` や `X_API_KEY` は認識されません |

## 鍵をなくした・漏れたときは

鍵はパスワードのように書き換えられません。「古いものを無効にして、新しいものを作る」しかありません。

1. **システム → 鍵管理** で、問題の鍵を**削除**します。
2. 新しい鍵を作り、文字列をコピーします。
3. 古い鍵を使っていた箇所（スクリプト・クライアント・ツールの設定）をすべて新しい鍵に置き換えます。

:::warning[漏れたときはまずこれを]
古い鍵の削除が最優先です。削除した瞬間にその鍵は使えなくなるため、他人の手に渡っていても使われません。新しい鍵はパスワードと同じように扱い、チャットや掲示板、コードの保管場所には貼らないでください。
:::

日ごろの心がけとして、次をおすすめします。

- **用途ごとに分ける**：バックアップ用を一本、スマホ用を一本。問題が起きた鍵だけを無効にできます。
- **ウェブの表側に置かない**：ブラウザの通信一覧に鍵が見えてしまい、それは公開と同じです。サーバー側か手元の機器に置いてください。
- **時々入れ替える**：削除して作り直せば、それが一回の入れ替えになります。
- **基本は家庭内ネットワークで使う**：オープン API を外部に公開するのは避けたいところです。必要なときは、手前にログインのしくみをもう一枚かぶせてください。

## 入れてもらえないときの見え方

認証に失敗しても AMMDS は答えを返します。ただ中の `code` が `401` になります。

```json
{
  "code": 401,
  "message": "您的登录已过期，请重新登录",
  "data": null,
  "timestamp": 1753958400000
}
```

`message` はサーバーが実際に返す文面で、中国語です。意味は「ログインの有効期限が切れました」。

次の順に確認してください。

1. オープン API のスイッチは ON になっていますか。
2. ヘッダー名は `x-api-key`（小文字・ハイフン）になっていますか。
3. 鍵の種別は X-API-KEY ですか。
4. 鍵は削除されたり作り直されたりしていませんか。
5. その住所は本当に `/api/v1` の配下ですか。（鍵を持ったまま管理側へ行くと拒否されます。これは意図した動作です。）

## うまくいかないときは

- **`401` が毎回返る**：上の五つを順に確認してください。多いのはスイッチが OFF な場合と、鍵の種別違いです。
- **鍵のコピーが途中で切れている**：削除して作り直し、最初と最後の文字を落とさないようにコピーしてください。
- **鍵を付けると管理側のインターフェースが使えなくなる**：仕様です。鍵が開けるのは `/api/v1` だけで、長期の鍵でログイン記録を飛び越せないようにしています。
- **来客用に鍵を渡したい**：おすすめしません。鍵の権限は自分のアカウントと同じで、利用者ごとのログイン記録も残らないため、後から追跡できません。
