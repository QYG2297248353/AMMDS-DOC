"무엇을 만들 것인가"를 정한 뒤 다음 문제는 "무엇으로 만들 것인가"였습니다. 이 문제를 두고 저희는 약 한 달간 진지하게 논쟁하며 네 가지 기술 노선을 평가했습니다. 이 글은 당시의 선택과 고민을 빠짐없이 기록한 것입니다.

## 네 가지 후보 노선

| 기술 스택 | 장점 | 저희가 우려한 점 |
| :--- | :--- | :--- |
| Python + Django | 개발 효율이 높음 | 배포 의존성이 무겁고 소스 코드 보호가 어려움 |
| Rust + Tauri | 성능과 보안이 뛰어남 | 개발 기간이 길고 웹 생태계 지원이 제한적 |
| Go + Web | 컴파일이 빠르고 단일 바이너리로 배포 | 제네릭과 프레임워크 생태계가 상대적으로 약함 |
| Java SpringBoot + Vue3 | 생태계가 성숙하고 인프라가 풍부함 | 전통적으로 런타임이 무거움 |

최종적으로 저희는 **Java SpringBoot + Vue3**를 선택했습니다. 백엔드는 SpringBoot 3.x로 RESTful API를 구축하고, 프론트엔드는 Vue3으로 인터랙션 경험을 제공합니다.

## 결정적 요인: GraalVM AOT

저울추를 결정적으로 기울게 한 것은 GraalVM Native Image의 AOT(Ahead-of-Time, 사전 컴파일) 능력이었습니다.

전통적인 Java 애플리케이션은 사용자가 먼저 JVM을 설치해야 합니다. 하지만 GraalVM을 사용하면 SpringBoot 애플리케이션을 독립 실행형 바이너리 실행 파일로 직접 컴파일할 수 있습니다:

- 사용자가 내려받아 바로 실행하며, **JVM을 설치할 필요가 없습니다**;
- 프론트엔드가 애플리케이션에 포함되어 **Node.js 환경이 필요 없습니다**;
- 내장 데이터베이스를 사용해 **별도 설정이 필요 없습니다**.

셀프 호스팅 제품에게 이것은 큰 이점입니다. 저희는 이미 사용자에게 "직접 기기를 준비해야 한다"는 진입 장벽을 지게 했으므로, 여기에 "직접 런타임을 구성해야 한다"는 부담을 더할 수는 없습니다. 동시에 네이티브 바이너리로 컴파일하면 백엔드 코드를 효과적으로 보호해 소스 코드 유출 위험을 줄일 수 있습니다.

## 두 번째 요인: 가상 스레드

AMMDS의 전형적인 작업 시나리오는 여러 사이트에서 동시에 데이터를 가져오고 응답을 파싱하며 파일에 기록하는 것으로, 전형적인 I/O 집약적 작업입니다.

SpringBoot의 가상 스레드(Virtual Threads)와 반응형 프로그래밍 모델은 바로 이런 시나리오에 적합합니다. 다수의 동시 I/O 대기를 무거운 시스템 스레드를 하나씩 점유하지 않고도 효율적으로 스케줄링할 수 있기 때문입니다. 덕분에 "여러 출처를 동시에 스크래핑"하는 것이 빠르면서도 자원을 절약할 수 있습니다.

## 사후 평가

오늘 돌아보면 이 선택은 시간의 시험을 견디었습니다:

- 플러그인 기반 아키텍처, 파이프라인 방식 데이터 처리, 가상 스레드 스케줄링 같은 핵심 설계가 모두 이 기술 스택 위에 구축되어 지금까지 이어지고 있습니다;
- 네이티브 바이너리 배포로 "내려받아 바로 사용"이 현실이 되었고, 설치 진입 장벽이 크게 낮아졌습니다;
- 성숙한 생태계 덕분에 저희는 바퀴를 다시 만드는 대신 제품 로직에 집중할 수 있었습니다.

기술 선택에 절대적으로 옳은 답은 없으며, "현재의 문제에 맞는가"만 있을 뿐입니다. 당시의 AMMDS에는 Java + Vue + GraalVM이 옳은 선택이었습니다.
