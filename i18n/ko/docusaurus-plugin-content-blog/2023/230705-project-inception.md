제품에 가장 자주 던져지는 질문은 "도대체 어떤 문제를 해결하느냐"입니다. AMMDS의 답은 회의실에 앉아 떠올린 것이 아니라, 저희가 매일 사용하던 도구 사슬 속에서 조금씩 다듬어진 것입니다.

## 출발점: 모두 도구에 시달려 본 사람들

멍선 스튜디오 팀원 모두 노련한 셀프 호스팅 사용자입니다. 하드디스크에는 수년간 쌓인 미디어 파일이 들어 있고, 이름 짓기부터 분류까지 저마다의 규칙이 있습니다. 저희는 동시에 PT 사이트의 헤비 사용자이기도 하며, 평소 IYUUPlus로 사이트 자원을 관리합니다.

이처럼 깊이 사용했기에 '단절'의 고통을 더욱 절실히 느낄 수 있었습니다.

## 단절된 도구 사슬

한 묶음의 미디어 파일을 보고 검색할 수 있는 미디어 라이브러리로 정리하려면, 당시의 도구 생태계에서는 다음이 필요했습니다:

- TinyMediaManager로 영화 메타데이터를 스크래핑하고;
- MediaElch로 드라마 정보를 처리하고;
- 별도의 도구로 사이트 자원을 관리하고;
- 또 다른 도구로 NFO 파일 형식의 일관성을 유지해야 했습니다.

각 도구는 저마다 데이터 형식과 조작 논리를 가지고 있었습니다. 데이터가 도구 사이를 오갈 때 정보가 자주 유실되었습니다 — A 도구에 입력한 출연진 정보가 B 도구에서는 사라지기도 했고, 어렵게 통일한 이름이 C 도구에서 다시 바뀌기도 했습니다.

## 아무도 진지하게 다루지 않은 두 가지 문제

매일 반복되는 사용 속에서 저희는 되풀이되는 두 가지 문제를 발견했습니다:

**첫째, 통합된 패널이 없습니다.** 한곳에서 모든 미디어 파일의 메타데이터 상태를 볼 수 없습니다. 어떤 항목은 스크래핑이 완료되었는지, 어떤 항목은 표지가 없는지, 어떤 항목은 출연진 정보가 틀렸는지 — 이런 질문에 답하려면 여러 도구 사이를 오가야 했습니다.

**둘째, 일괄 수정이 불가능합니다.** 스크래핑 결과가 틀렸을 때 하나씩 수동으로 고칠 수밖에 없습니다. 수십 TB 규모의 미디어 라이브러리를 가진 헤비 사용자에게 이런 반복 작업의 유지보수 비용은 엄청납니다.

## 프로젝트 착수에 대한 판단

저희는 부족한 것이 또 다른 "더 쓰기 좋은 단일 기능 도구"가 아니라, 이 도구 사슬 전체를 하나로 잇는 무언가라는 점을 깨달았습니다:

> 한곳에서 메타데이터 스크래핑부터 사이트 자원 관리, 미디어 라이브러리 구축에 이르는 전체 흐름을 완결하는 것.

이 판단이 AMMDS 프로젝트 착수의 출발점이 되었습니다. 이후 제품의 많은 특징 — 통합 웹 패널, 배치 처리 기능, 여러 출처의 데이터 병합 — 이 모두 같은 목표를 향했습니다. 바로 사용자가 더 이상 도구 사이에서 데이터를 옮기지 않도록 하는 것이었습니다.

물론 "무엇을 해결할 것인가"에서 "어떻게 해결할 것인가"까지는 기술 선택이라는 한 과정이 남아 있었습니다. 그것이 다음 글에서 다룰 이야기입니다.
