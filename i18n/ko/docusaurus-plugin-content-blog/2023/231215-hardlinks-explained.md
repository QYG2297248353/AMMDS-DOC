셀프 호스팅 미디어 라이브러리에는 거의 모두가 한 번쯤 빠지는 함정이 있습니다. 다운로드 디렉터리에는 시딩을 위해 원본 파일을 남겨 두어야 하고, 미디어 라이브러리에는 깔끔하고 규범적인 이름을 원하는 것이죠. 그래서 같은 40GB 짜리 영화가 두 벌로 저장되고 80GB가 그렇게 사라집니다. 하드 링크는 바로 이 문제를 해결하기 위해 생겨났습니다.

## 복사가 잘못된 이유

먼저 갈등이 어디에서 오는지 분명히 하겠습니다.

- **다운로더**(예: qBittorrent)는 계속 시딩하려면 원본 파일명과 디렉터리 구조가 바뀌지 않아야 합니다.
- **미디어 서버**(Jellyfin, Emby 등)는 메타데이터를 올바르게 인식하고 매칭하려면 `영화명 (연도)/영화명 (연도).mkv` 같은 규범적인 이름이 필요합니다.

파일을 다운로드 디렉터리에서 미디어 라이브러리로 **복사**하면 40GB 짜리 4K 영화가 순식간에 80GB가 됩니다. 공간을 차지하는 것뿐 아니라 복사는 디스크를 실제로 한 번 읽고 쓰기 때문에 큰 파일은 오래 걸립니다.

## 하드 링크가 해결하는 방법

파일 시스템에서 하나의 파일은 사실 두 부분으로 나뉩니다. 실제 데이터를 담는 **데이터 블록**과 그것을 가리키는 **디렉터리 항목**(이름이라고 생각하면 됩니다)입니다.

일반적인 복사는 새 데이터와 새 이름을 만듭니다. 반면 하드 링크는 **같은 데이터를 가리키는 이름 하나를 더 추가**할 뿐입니다.

- **추가 공간을 차지하지 않음**: 두 경로가 같은 바이트를 보므로 영화는 한 번만 저장됩니다.
- **순식간에 완료**: 파일이 100GB든 1GB든 링크를 만드는 것은 새 이름을 등록하는 일이라 밀리초 단위입니다.
- **양쪽 모두 이름 변경 가능**: 미디어 라이브러리에서 규범적인 이름으로 바꿔도 다운로드 디렉터리의 원본 파일과 시딩에는 영향을 주지 않습니다.
- **삭제 시 안전**: 마지막 이름까지 삭제될 때만 데이터가 실제로 해제됩니다. 시딩용 파일을 지워도 미디어 라이브러리의 파일은 그대로 남습니다.

## 핵심 전제 조건: 같은 파일 시스템

하드 링크는 파일 시스템 수준의 기능으로, 한 가지 단단한 제약이 있습니다. **같은 파티션 / 볼륨 안에서만 만들 수 있습니다.**

이 제약은 컨테이너 환경에서 가장 자주 문제를 일으킵니다. 많은 사람이 Sonarr와 Radarr에 `/downloads`와 `/media` 두 경로를 각각 마운트합니다. 호스트에서는 같은 디스크에 있어도 컨테이너 안에서는 서로 다른 마운트 지점이므로 커널이 장치 간 이동으로 판단해 `link()` 호출이 실패하고(`EXDEV` 오류) 소프트웨어는 **조용히 복사로 되돌아갑니다**. 화면에서는 이상한 점을 전혀 볼 수 없고, 디스크만 빠르게 채워집니다.

올바른 방법은 모든 컨테이너가 같은 디렉터리 트리를 보게 하는 것입니다. 예컨대 통일된 `/data`입니다.

```text
/data
├── torrents/     ← 다운로더가 여기에 저장
└── media/        ← 미디어 라이브러리가 여기에 저장
```

Sonarr / Radarr에서는 다음 설정이 켜져 있는지도 확인해야 합니다. `Settings → Media Management → Importing → Use Hardlinks instead of Copy`(기본값으로 켜져 있습니다).

## AMMDS와의 관계

AMMDS가 맡는 것은 "검색 → 구독 → 다운로더로 전달 → 정리하여 라이브러리에 저장"이라는 흐름의 후반부입니다. 하드 링크를 이해하면 공간을 낭비하지 않고 전체 흐름을 연결할 수 있습니다. 다운로더는 제자리에서 시딩하고, AMMDS는 규범적인 미디어 라이브러리를 정리하며, 둘은 같은 데이터를 공유합니다. 이는 AMMDS만의 기능이 아니라 셀프 호스팅 미디어 라이브러리라는 조합의 기본기입니다.

> 참고: 이 글의 기술적 세부 사항은 공개된 미디어 서버 배포 가이드(TRaSH Guides 등)를 바탕으로 정리했습니다. 하드 링크의 구체적인 동작은 사용하는 파일 시스템과 컨테이너 구성에 따라 달라집니다.
