# AMMDS, 개념에서 현실로: 제품 탄생기

오늘은 AMMDS 뒤에 숨은 이야기를 들려드리고자 합니다. 막연한 아이디어에서 최종 제품에 이르기까지, 이 개발 여정은 도전과 결정, 성장으로 가득했습니다.

## 시장 수요: 기존 도구로는 부족했다

이야기의 출발점은 저희 스스로의 "고충"이었습니다. 멍선 스튜디오 팀원들은 모두 노련한 자체 호스팅 사용자로, 일상에서 IYUUPlus로 사이트 자원을 관리하며 보편적인 문제 하나를 발견했습니다:

**미디어 관리 도구 사슬이 단절되어 있다.**

TinyMediaManager로 영화 메타데이터를 스크래핑하고, MediaElch로 드라마 정보를 처리하고, 별도 도구로 사이트 자원을 관리하고, 또 다른 도구로 NFO 파일 형식의 일관성을 유지해야 합니다. 각 도구는 저마다 데이터 형식과 조작 논리가 달라, 데이터가 도구 사이를 오갈 때 정보가 자주 유실됩니다.

무엇보다 기존 도구는 대부분 통합 대시보드와 자동화 기능이 부족합니다. 한곳에서 모든 미디어 파일의 메타데이터 상태를 볼 수도 없고, 잘못된 스크래핑 결과를 일괄 수정할 수도 없습니다. 수십 TB 규모 미디어 라이브러리를 가진 헤비 사용자에게 이 단절은 엄청난 유지보수 비용으로 이어집니다.

## 기술 선택: Java SpringBoot + Vue3를 고른 이유

무엇을 만들지 정한 뒤 다음 문제는 무엇으로 구현할 것인가였습니다.

저희는 한 달간 기술 조사를 진행하며 다양한 기술 스택을 평가했습니다:

- **Python + Django**: 개발 효율은 높지만 배포 의존성이 무겁고 소스 코드 보호가 어렵습니다
- **Rust + Tauri**: 성능과 보안이 뛰어나지만 개발 기간이 길고 웹 생태계 지원이 제한적입니다
- **Go + Web**: 컴파일 속도가 빠르고 단일 바이너리로 배포할 수 있지만 제네릭과 프레임워크 생태계가 상대적으로 약합니다
- **Java SpringBoot + Vue3**: 성숙한 생태계, 풍부한 인프라, GraalVM AOT 네이티브 컴파일로 코드를 바이너리로 보호

최종적으로 저희는 **Java SpringBoot + Vue3** 조합을 선택했습니다. 백엔드는 SpringBoot 3.x 프레임워크로 RESTful API를 구축하고, 프론트엔드는 Vue3으로 현대적인 인터랙션 경험을 제공합니다. GraalVM Native Image의 AOT(Ahead-of-Time) 컴파일 기술을 통해 SpringBoot 애플리케이션을 독립 실행형 바이너리 실행 파일로 직접 컴파일할 수 있어, 사용자가 내려받아 바로 실행할 수 있고 JVM 런타임을 설치할 필요가 없습니다. 이는 자체 호스팅 환경에서 큰 이점입니다. 사용자는 Java 런타임이나 Node.js 환경을 설치하거나 데이터베이스를 설정할 필요가 없습니다.

동시에 SpringBoot의 가상 스레드(Virtual Threads)와 반응형 프로그래밍 모델은 스크래핑 작업 처리에 매우 적합합니다. AMMDS의 전형적인 작업 시나리오는 여러 사이트에서 동시에 데이터를 가져오고 응답을 파싱하며 파일에 기록하는 것으로, 이러한 I/O 집약적 작업은 가상 스레드 스케줄링 모델에서 매우 뛰어난 성능을 보입니다. 또한 GraalVM 네이티브 바이너리는 백엔드 코드를 효과적으로 보호해 소스 코드 유출을 방지합니다.

## 주요 결정 노드

### 첫 번째 결정: 플러그인 기반 아키텍처

프로젝트 설계 초기부터 저희는 **플러그인 기반 아키텍처**를 핵심 설계 원칙으로 삼았습니다. 즉 AMMDS의 스크래핑 엔진, 사이트 어댑터, 데이터 처리 흐름이 모두 플러그 방식이라는 뜻입니다. 사용자는 필요에 따라 다양한 플러그인을 설치할 수 있고, 커뮤니티도 서드파티 플러그인을 기여해 기능을 확장할 수 있습니다.

이 결정은 이후 개발 과정에서 매우 올바른 선택임이 입증되었습니다. AMMDS가 여러 PT 사이트와 메타데이터 소스를 빠르게 지원할 수 있는 것도, 플러그인 기반 아키텍처 덕분에 핵심 코드를 수정하지 않고 플러그인을 작성만 해서 새 사이트를 지원할 수 있었기 때문입니다.

### 두 번째 결정: 웹 대시보드 우선

전통적인 미디어 관리 도구와 달리, 저희는 데스크톱 클라이언트가 아닌 웹 대시보드를 AMMDS의 주된 인터페이스로 삼기로 했습니다. 이는 사용자가 PC, 태블릿, 휴대폰은 물론 NAS의 브라우저를 통해서도 어느 기기에서든 미디어 라이브러리를 관리할 수 있다는 뜻입니다.

웹 대시보드의 설계는 '모바일 우선' 철학도 반영해, 휴대폰 화면에서도 좋은 조작 경험을 보장합니다.

### 세 번째 결정: NFO 표준 호환

커뮤니티에서는 NFO 파일 형식을 둘러싸고 늘 논란이 있어 왔습니다. Kodi의 NFO 형식, Jellyfin의 NFO 형식, Emby의 NFO 형식 사이에 미세한 차이가 있기 때문입니다. 저희는 **모든 주류 형식을 동시에 지원하기로** 했습니다. 사용자가 설정에서 대상 형식을 선택하면 시스템이 자동으로 맞춰 줍니다.

## 첫 번째 프로토타입

2023년 말, AMMDS의 첫 실행 가능한 프로토타입이 탄생했습니다. 이 버전은 가장 기초적인 기능만 갖추고 있었습니다:
- 단일 사이트에서 토렌트 목록 가져오기
- 토렌트의 메타데이터 정보 파싱
- 기본 NFO 파일 생성

기능은 조촐했지만 핵심 기술 노선의 실현 가능성을 검증했습니다. 오늘날 되돌아보면 이 프로토타입의 코드는 여러 번 다시 작성되었지만, 플러그인 엔진, 파이프라인 방식 데이터 처리, 가상 스레드 기반 스케줄링 시스템 같은 핵심 아키텍처 설계는 지금까지 그대로 이어지고 있습니다.

## 개발 과정의 과제

### 과제 1: 사이트 호환성

PT 사이트는 제각기 다른 페이지 구조, 인증 방식, 데이터 형식을 가지고 있습니다. 정적 페이지를 쓰는 곳도 있고, JavaScript로 동적으로 렌더링하는 곳도 있으며, API 인터페이스를 쓰는 곳도 있습니다. 서로 다른 사이트를 지원하기 위해 저희는 유연한 어댑터 메커니즘을 개발해 사이트마다 독립적인 파싱 규칙을 작성할 수 있게 했습니다.

### 과제 2: 데이터 일관성

여러 소스에서 같은 영화의 메타데이터를 동시에 가져올 때 이를 병합하고 중복을 제거하는 방법은 까다로운 문제입니다. 저희는 **우선순위 규칙 엔진**을 설계해 사용자가 서로 다른 정보 출처의 우선순위를 직접 정의하면 시스템이 규칙에 따라 자동으로 데이터를 병합하도록 했습니다.

### 과제 3: 성능 최적화

대규모 미디어 라이브러리(수만 건)를 처리할 때 메모리 사용량과 스캔 속도가 병목이 되었습니다. 증분 스캔, 캐시 메커니즘, 배치 처리 전략을 도입해 전체 스캔 시간을 몇 시간에서 수십 분으로 단축했습니다.

## 제품 진화

첫 프로토타입부터 오늘날의 AMMDS까지 제품은 수많은 반복과 리팩터링을 거쳤습니다. 모든 버전 업데이트는 사용자의 생생한 피드백과 개발자 자신의 사용 경험에서 비롯되었습니다. 저희는 '자기가 만든 것을 자기가 쓴다'는 원칙을 고수합니다. 팀원들이 평소 AMMDS로 자신의 미디어 라이브러리를 관리하기에 문제와 개선 방향을 가장 먼저 발견할 수 있습니다.

AMMDS는 여전히 빠르게 진화하고 있습니다. 앞으로 더 많은 지능형 메타데이터 처리 기능을 도입하고 플러그인 생태계를 더욱 완성해, 자체 호스팅 미디어 관리를 더 간단하고 효율적으로 만들겠습니다.
