AMMDS 설계 초기, 저희는 핵심 원칙 하나를 세웠습니다. 바로 플러그인 기반 아키텍처입니다. 이 글에서는 그 결정이 어떻게 내려졌는지, 그리고 그것이 왜 올바름으로 입증되었는지 이야기하겠습니다.

## 문제: 사이트는 언제나 하나만 있지 않다

프로토타입을 만들 때는 사이트 하나만 연결하면 되었습니다. 하지만 실제 미디어 라이브러리 사용자는 파편화된 생태계와 마주한다는 점은 분명했습니다:

- 서로 다른 PT 사이트는 저마다 페이지 구조, 인증 방식, 데이터 형식을 가지고 있습니다;
- 정적 페이지를 쓰는 곳이 있고, JavaScript로 동적으로 렌더링하는 곳이 있으며, API를 직접 공개하는 곳도 있습니다;
- 새로운 사이트와 자료 출처가 거의 매달 등장합니다.

각 사이트의 파싱 로직을 모두 핵심 코드에 넣는다면 결과는 불 보듯 뻔합니다. 코드는 점점 비대해지고, 사이트를 하나 추가할 때마다 주 줄기를 손봐야 하며, 커뮤니티도 참여할 수 없습니다. 저희는 '새 사이트 지원'을 국소적인 일로 만드는 방법이 필요했습니다.

## 결정: 변하는 부분을 플러그인으로 뽑아내다

저희가 최종적으로 채택한 아키텍처는 세 부분을 교체 가능하게 만들었습니다:

| 계층 | 역할 | 왜 교체 가능한가 |
| :--- | :--- | :--- |
| 스크래핑 엔진 | 작업 스케줄링, 결과 병합 | 핵심은 안정적이지만 전략은 교체 가능 |
| 사이트 어댑터 | 특정 사이트의 페이지/API 파싱 | 가장 자주 바뀌므로 반드시 분리 |
| 데이터 처리 흐름 | 메타데이터에서 NFO로의 변환 | 사용자마다 선호가 다름 |

이렇게 해서 핵심 코드는 '스케줄링과 조율'만 맡고, 구체적인 '어떻게 가져오고 어떻게 파싱할지'는 플러그인에 맡깁니다. 사용자는 필요에 따라 설치하고, 커뮤니티는 주 줄기를 전혀 수정하지 않고 서드파티 플러그인을 기여할 수 있습니다.

## 우선순위 규칙 엔진

플러그인화는 새로운 문제를 낳았습니다. 같은 영화에 대해 여러 출처에서 서로 다른 메타데이터를 가져왔을 때, 누구의 말을 들어야 할까요?

저희는 **우선순위 규칙 엔진**을 설계했습니다. 사용자가 서로 다른 정보 출처의 우선순위를 직접 정의하면 시스템이 규칙에 따라 자동으로 병합하고 중복을 제거합니다. 이렇게 하면 여러 출처의 풍부함은 유지하면서 최종 결정권은 사용자에게 돌려줄 수 있습니다. 이는 저희가 늘 지켜 온 '선택권은 사용자에게'라는 원칙에 부합합니다.

## 사후 검증

이 결정은 이후 개발 과정에서 거듭 그 가치를 입증했습니다:

- **빠른 대응**: AMMDS가 핵심 코드를 건드리지 않고 여러 PT 사이트와 메타데이터 출처를 잇달아 지원할 수 있었던 것은 바로 플러그인화 덕분입니다;
- **커뮤니티 참여**: 서드파티 플러그인 덕분에 생태계가 확장될 수 있었고, 모든 부담이 스튜디오에 쏠리지 않았습니다;
- **장애 격리**: 단일 사이트가 개편되면 보통 플러그인 하나만 고치면 되며, 전체 시스템에는 영향을 주지 않습니다.

프로토타입의 하드코딩된 파싱 스크립트부터 오늘의 이 교체 가능한 아키텍처까지, 저희가 투자한 기술 중 가장 값진 투자였습니다.
